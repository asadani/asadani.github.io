Amazon S3 Files

Breaking the
Object-File Barrier

How AWS S3 native NFS v4.1 support erases the decade-long architectural divide between object storage and high-performance file systems — and what it means for AI, ML, and enterprise architecture.

April 7, 2026 — General Availability NFSv4.1 · EFS Cache Layer · Sub-ms Latency Multi-TB/s Aggregate Throughput
OFFICIAL

Amazon S3 Files launched on April 7, 2026. This article covers the technical architecture, pricing model, and real-world implications. View the official AWS announcement →

For over a decade, cloud architects have lived in a bifurcated world: Amazon S3 for massive, cost-effective object storage, and Amazon EFS or FSx when applications demanded a real file system. The tax of bridging these two worlds — DataSync jobs, S3 File Gateways, pre-hydration pipelines — was a known cost of doing business at scale.

Amazon S3 Files changes that equation entirely. By embedding native NFSv4.1 support directly into S3 buckets, backed by EFS-powered caching technology, AWS has effectively converged object and file storage into a single, unified layer. The same bucket can now serve your REST API consumers and your NFS-mounted ML training jobs simultaneously, without any data duplication.

01
The Architecture Shift

The fundamental change here is deceptively simple: S3 buckets can now be mounted as file systems using standard NFS v4.1 clients. No gateway appliance. No data duplication. No sync delay. The S3 bucket is the file system.

The caching layer is the key technical insight. AWS uses Amazon EFS technology to maintain an active working set of metadata and small files in a high-performance cache, delivering sub-millisecond latency for hot data. Large files (>128 KB) stream directly from S3 to the NFS client, bypassing the cache entirely — which is also why large-file reads are effectively free under the new pricing model.

02
Who Wins — And How
⚡

ML / AI Training

Training pipelines interact with S3 as a local directory. PyTorch and TensorFlow data loaders work unmodified. GPUs stay saturated without pre-hydration waits. Aggregate throughput scales to multiple TB/s.

🤖

Agentic AI Systems

AI agents that use file-based Python tooling (pathlib, open()) can now share state and persist memory across distributed pipelines without custom S3 API wrappers. The S3 bucket becomes the agent's shared scratchpad.

🗂️

Legacy App Migration

Applications that assume a POSIX file system — CMS platforms, ERP systems, monolithic backends — can be lifted to cloud-native S3 storage without code changes. NFS mount replaces the old NAS or EFS volume.

🏗️

Simplified Architecture

Eliminate separate EFS volumes for app configs and S3 buckets for assets. One bucket serves both NFS-mounting services and REST API consumers simultaneously, from a single source of truth.

🔬

Scientific Computing

HPC workloads running across thousands of instances can now use S3 as a shared scratch space with NFS semantics, without provisioning and paying for a dedicated parallel file system like FSx for Lustre.

📊

Data Engineering

ETL pipelines that write intermediate results can use standard file operations against S3. No more choosing between S3 object semantics and temporary EFS volumes just to process a multi-TB Parquet dataset.

The Key Insight

We are moving from a "Copy-to-Compute" model to a true "Compute-on-Data" architecture. The GPU cluster comes to the data, not the other way around. For large-scale ML where dataset sizes dwarf GPU memory by orders of magnitude, this is a fundamental change in how training economics work.

03
Technical Architecture

The implementation details matter for understanding when S3 Files excels and where its boundaries are. Here is what the engineering looks like under the hood:

  • Protocol: NFSv4.1 — not v3, not v4.0. v4.1 is significant because it provides compound operations, better caching semantics, and pNFS support for parallel file access across multiple servers.
  • Consistency Model: Close-to-open consistency. Changes written by one NFS client become visible to other clients after the writing client closes the file. This is the same model as Amazon EFS and works well for shared read-heavy workloads.
  • Cache Architecture: EFS-powered. Active metadata and small files (<128 KB) are cached in a high-performance EFS layer. Cache state is managed automatically — you don't provision or manage it.
  • Large File Path: Files >128 KB bypass the EFS cache layer entirely and stream directly from S3. This delivers full S3 throughput for large sequential reads (the dominant access pattern for ML training).
  • Throughput Ceiling: Aggregate throughput scales to multiple TB/s across concurrent clients. This is a function of S3's distributed architecture, not a single-node file system limit.
  • Durability: Inherits S3's 11-nines durability. Data written via NFS is committed to S3 storage — the cache is a read/write performance accelerator, not the durable store.
  • S3 Metadata Integration: Works with the new S3 Metadata feature for fast directory listings and file attribute queries at millions-of-objects scale.
  • IAM Integration: Permissions are governed by standard S3 bucket policies and IAM. POSIX UID/GID are handled via a mapping layer.
04
Pricing Model

The pricing model reflects the hybrid architecture: you pay standard S3 rates for storage at rest, plus data-access surcharges for the caching and movement overhead introduced by NFS operations. Understanding the large-file free-read rule is critical for sizing the cost correctly.

Pricing Component Rate Notes
Data at Rest (S3 Standard) $0.023 / GB-mo Standard S3 pricing. S3-IT tiers apply as normal.
Cache Storage (EFS layer) $0.30 / GB-mo Only charged for the active working set in cache — typically 1–5% of total bucket size.
NFS Writes $0.06 / GB All data written via NFS goes through the cache layer first, then syncs to S3.
NFS Reads — Small (<128 KB) $0.03 / GB First-read "import" to cache costs $0.06/GB; subsequent reads of same file cost $0.03/GB.
NFS Reads — Large (>128 KB) FREE Large files stream directly from S3. Standard S3 GET request fees only (~$0.0004/1000 GETs).
The ML Training Sweet Spot

ML training datasets are almost entirely large files — multi-GB Parquet shards, TFRecords, checkpoint files. Under S3 Files pricing, large-file reads are essentially free, making it dramatically cheaper than EFS ($0.30/GB-mo) for the massive, read-heavy access patterns that define model training at scale.

07
Honest Trade-offs

No architecture decision is universally correct. Here is a balanced view of where S3 Files adds undeniable value and where the trade-offs warrant careful thought:

Advantages

  • Eliminates data duplication between EFS and S3
  • No DataSync or File Gateway to manage or pay for
  • Large-file reads are essentially free — massive win for ML workloads
  • Single IAM policy governs both NFS and REST access
  • Inherits S3's 11-nines durability automatically
  • Architecture diagrams get dramatically simpler
  • Compatible with S3 Intelligent-Tiering for cost optimization

Considerations

  • $0.06/GB write fee — expensive for heavy-write workloads (logging, scratch space)
  • Small-file read overhead — randomized access to millions of tiny files will accumulate fees
  • Close-to-open consistency: last-writer-wins under concurrent writes requires app-level coordination
  • Deep recursive directory scans still slower than local NVMe
  • Cold cache on first read introduces latency spike for first-time file access
  • May not fully replace FSx for Lustre for striped, low-latency HPC scratch at extreme scale
Cost Warning

If your workload is write-heavy — compiling code, rotating log files, frequent checkpoint saves — the $0.06/GB NFS write fee can add up fast. For intensive ephemeral scratch space, pure EFS or local NVMe may still be the right call. Run the estimator above with your actual write volume before migrating.

The Bottom Line

Amazon S3 Files is the most significant change to AWS storage architecture in years. It doesn't just add a feature to S3 — it eliminates an entire category of infrastructure complexity that teams have been building workarounds for since 2006.

For AI and ML teams, the value is immediate and measurable: no more pre-hydration steps, no more managing separate EFS volumes per training cluster, no more data duplication costs. The GPU cluster talks directly to S3 via NFS, and the economics (especially the free large-file reads) make it the obvious default for any read-heavy training workload.

For platform engineers and architects, the convergence of object and file APIs on a single data layer opens up a class of architectures that simply wasn't practical before — truly unified data planes where the same dataset is queryable by S3 Select, accessible via NFS by legacy apps, and consumed by modern REST APIs, all without a line of synchronization code.

The open question is whether this makes FSx for Lustre obsolete for extreme-scale HPC. For most teams — even those running large GPU clusters — S3 Files will be sufficient. For the edge cases that need striped, sub-millisecond access to petabytes of scratch space, Lustre still has a role. But that edge just got much smaller.
