The comparison that changed the recommendation.

I had no human participants, so I commissioned a separate Claude Code agent evaluation. One builder used the framework; another implemented equivalent application controls for the same purchase-order requirements. Both then handled a policy change and an investigation.

This was one paired pilot, independent of the framework builder, using the same model for both arms. It gave me a concrete integration comparison:

Both implementations passed twenty six out of twenty six visible acceptance tests, and one hundred and fourteen out of one hundred and fifteen held-out tests. Both passed fifteen out of fifteen policy-change tests and scored forty eight out of forty eight on investigation. The framework builder used forty five tool calls, versus thirty four for the application builder. The policy change took thirty two tool calls in the framework arm and twenty in the application arm. The framework had eight library-contract workarounds; the application had none. The held-out suite took thirty nine point six seconds with the framework and four point five seconds with the application.

The framework required eight library-contract workarounds and seven core-change requests. The builder duplicated checks to obtain specific refusal reasons before calling it. Reuse was fighting the integration.

Both failed the same held-out approval-after-outage case because the spec was ambiguous; no downstream effect occurred. The baseline’s zero workarounds refers to library contracts, not its two test and path adjustments.

The three hundred and seventy four-line spec supplied much of the lifecycle design. Investigators had downstream exports and a harness problem prevented operator-CLI use. A spend-limit interruption also affected the framework build. Tool calls are not developer hours, and these conditions limit generalisation. Full comparison and deviations.

The independent evaluator recommended: “Stop feature expansion and adoption and migration claims.”
